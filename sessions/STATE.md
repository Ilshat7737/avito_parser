## Готово

- Фича «две поисковые сессии» веб-режима `avito_parser`: session_id ∈
  {1, 2}, чередование в одном потоке (без параллельного скрапинга),
  кросс-сессионный дедуп на 24 часа (только для релевантных объявлений),
  атомарная миграция существующей БД на новую схему.
- Полный цикл задания пройден: контекст (`AGENTS.md`) → спецификация
  (`SPEC.md`) → наивный прогон (отдельная ветка/worktree, для сравнения)
  → реализация по спеке через `subagent-driven-development` (5 задач,
  каждая с ревью + при находках — фикс-раундом) → финальное ревью всей
  ветки (Opus) → фикс-раунд по его находкам → повторное ревью (чисто).
- Тесты: 74/74 проходят (`python3 -m pytest -v`).
- Ручная проверка: живой запуск `python app.py`, две независимые
  сессии подтверждены визуально (скриншоты в `sessions/screenshots/`)
  и через API (curl), пауза одной сессии не блокирует другую, `?session=`
  с некорректным значением → 400.
- Ветка смержена в `main`, запушена на GitHub
  (`git@github.com:Ilshat7737/avito_parser.git`).
- По просьбе пользователя убран весь учебный «мусор» и структура
  выровнена под обычный проект: `TestTask/materials/` и `homework.pdf`
  удалены, а `AGENTS.md`/`SPEC.md`/`sessions/` перенесены из `TestTask/`
  в корень репозитория и объединены с уже существующими корневыми
  `CLAUDE.md`/`README.md` (было по два файла на каждую роль — теперь по
  одному). Подпапки `TestTask/` в репозитории больше нет.
- Визуальный редизайн интерфейса (веб-режим): automotive-тема, у каждой
  сессии свой акцентный цвет (янтарный/голубой), переключатель сессий —
  сегмент-табы со статусом обеих сессий сразу, часть компонентов — с
  21st.dev (`Status`, стиль «Segmented Control Tabs»). Логика не
  менялась — только `index.css`, `tailwind.config.ts`, вёрстка
  компонентов, новый `SessionSwitcher.tsx`.
- Ручной прогон пользователя на реальных данных (свой `GEMINI_API_KEY`,
  реальный Avito) нашёл и привёл к исправлению двух реальных проблем:
  (1) объявление, на котором агент не смог ответить (сбой/перегрузка
  Gemini API), раньше терялось насовсем в этом цикле — теперь
  показывается как есть, без оценки, а не молча пропускается; (2)
  объявления писались в БД пачками по 15 (`agent.BATCH_SIZE`) — при
  реальных задержках 20–30 сек между запросами это держало найденные
  карточки невидимыми до 7+ минут; теперь каждое объявление обрабатывается
  и показывается по одному, сразу как готово. `CHUNK_SIZE` убран.

## Не начато

- Живая проверка миграции БД на реальном файле пользователя с историей
  (не на синтетических данных) — файла `avito_monitor_web.db` от
  прошлых запусков в репозитории не нашлось на момент проверки (сейчас
  такой файл уже появился в ходе ручного прогона, но остался локальным
  файлом пользователя, не частью репозитория — миграция на нём не
  проверялась намеренно, чтобы не превращать чужие реальные данные в
  тестовый артефакт).
- Сессия 2 ни разу не получила реального цикла скрапинга за время
  ручного прогона — первый цикл сессии 1 (широкий фильтр, много
  подходящих объявлений) не успел закончиться. Не баг — прямое
  следствие чередования вместо параллельности, но воспринимается на
  практике куда медленнее, чем ожидал пользователь. Не менялось
  архитектурно в этой сессии — открытый вопрос на будущее: устраивает
  ли такая цена компромисса на практике или стоит пересмотреть.

## Известные проблемы

- При единственной настроенной сессии до фикс-раунда финального ревью
  частота опроса Avito ошибочно падала вдвое — **починено**, но стоит
  помнить при следующей доработке `background_loop`: любая новая ветка
  условия там должна явно решить, короткий у неё wait (как у паузы/
  неготовой сессии) или полный интервал.
- Несколько Minor-находок ревью оставлены как есть осознанно (не
  блокируют функциональность) — полный список рулингов в
  `.superpowers/sdd/2026-08-28-two-search-sessions/progress.md`:
  голый `ROLLBACK` в `except BaseException` миграции без вложенной
  защиты; дублирование блока валидации `session_id` в 7 хендлерах
  `app.py`; `int(raw)` в `_parse_session_id` молча округляет дробные
  значения; неявный порядок колонок в `INSERT ... SELECT *` для
  `search_config`/`worker_status` внутри `_migrate_to_sessions`.
