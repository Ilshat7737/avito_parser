# Дизайн: веб-версия монитора для поиска машин на Avito

Дата: 2026-08-13
Статус: одобрено пользователем в брейнсторминге, готово к написанию плана реализации

## Контекст и цель

Текущий проект — CLI-скрипт (`main.py`), запускаемый вручную или по cron, с
настройками только через `config.py` и уведомлениями в консоль/Telegram.

Новая задача: превратить его в локальное веб-приложение для поиска **машин**
на Avito, с:
- вводом критериев поиска (город, марка, диапазон цены, диапазон пробега,
  диапазон года, произвольное текстовое уточнение) через браузер, а не
  `config.py`;
- LLM-агентом, который фильтрует и ранжирует найденные объявления по
  релевантности текстовому уточнению;
- автообновлением данных раз в минуту;
- строгим лимитом на размер БД (100 записей с полными данными), чтобы не
  забить диск, при этом без повторного скачивания уже виденных объявлений;
- красивым, легко читаемым веб-интерфейсом (React + Tailwind +
  shadcn/21st.dev компоненты, дизайн-система от ui-ux-pro-max).

Это архитектурная переработка: меняется способ ввода данных, добавляется
постоянно работающий сервер, LLM-интеграция и полноценный frontend-стек
(Node.js/npm) там, где раньше был только Python.

## Архитектура

Flask-приложение с двумя параллельно работающими частями, читающими и
пишущими одну и ту же SQLite-базу:

- **Фоновый поток** (`threading.Thread`, daemon) — аналог сегодняшнего
  `main_loop`, но живёт внутри веб-процесса и крутится с интервалом ~60 сек
  (не непрерывный/ручной запуск через `python main.py`, а часть
  веб-приложения). Каждый цикл: скрапинг → dedup → (для новых) описание →
  батч-вызов агента → запись в БД → уведомления.
- **Flask-сервер** — отдаёт собранный React-фронтенд (`frontend/dist`) как
  статику и JSON через `/api/*`. Сам ничего не скрапит, только читает/пишет
  БД и по запросу с фронта пересобирает `search_url` (см. ниже).

Браузер открывает `http://localhost:5000`, JS на странице каждые 60 сек
опрашивает `/api/listings` и `/api/status` и перерисовывает список —
независимо от фонового потока (оба просто читают ту же БД).

`main.py --once` в консольном режиме (без веб-интерфейса) можно оставить как
есть — полезен для отладки скрапинга без поднятия сервера.

### Жизненный цикл одного цикла опроса

1. Фоновый поток берёт текущий `search_url` из таблицы `search_config`.
2. Парсит карточки со страницы поиска (как сегодня в `scraper.py`).
3. Для каждой карточки — dedup-логика (детали в разделе БД):
   - уже в `listings` (не вытеснен) → обычная проверка цены/`touch`;
   - уже в `seen_ids`, но не в `listings` (вытеснен лимитом) → пропустить
     полностью, не трогать;
   - совсем новый `id` → тянуть полное описание → добавить в очередь на
     оценку агентом.
4. Все новые карточки этого цикла разом (один батч-запрос) отправляются в
   `agent.py` вместе с текущим текстовым уточнением из `search_config`.
   Агент возвращает для каждой `{relevant: bool, reason: str}`.
5. Все новые карточки пишутся в `listings` (полные данные) и `seen_ids`
   (только `id`), независимо от вердикта агента — чтобы `relevant=0`
   тоже не переоценивались повторно.
6. Уведомления (консоль/Telegram + toast в браузере) — только для карточек с
   `relevant=1`.
7. После вставки — обрезка `listings` до 100 самых свежих строк по
   `first_seen` (см. раздел БД).

## Хранилище данных

### Таблица `listings` (изменена)

Существующие столбцы (`id, title, price, url, photo, description, first_seen,
last_price, last_checked`) плюс новые:

- `year INTEGER` — год выпуска
- `mileage INTEGER` — пробег
- `relevant INTEGER` — `NULL` = не оценено, `1` = релевантно, `0` = отклонено
- `relevance_reason TEXT` — короткое обоснование от агента
- `agent_evaluated_at TEXT` — момент оценки (NULL, пока не оценено)

**Жёсткий лимит на 100 строк.** После каждой вставки новых записей:

```sql
DELETE FROM listings
WHERE id NOT IN (SELECT id FROM listings ORDER BY first_seen DESC LIMIT 100)
```

Ошибка вызова агента для конкретной карточки в рамках цикла **не** должна
приводить к её удалению/пропуску навсегда: если батч-вызов агента упал
(rate limit, timeout, некорректный ответ), такие карточки просто не
вставляются в `listings`/`seen_ids` в этом цикле и будут повторно
обработаны на следующем.

### Таблица `seen_ids` (новая, без ограничения размера)

```sql
CREATE TABLE seen_ids (id TEXT PRIMARY KEY, first_seen TEXT)
```

Хранит только `id` и дату первого обнаружения — без description/photo/текста,
поэтому рост неограничен по времени, но пренебрежимо мал по месту (даже
100 000 записей — около 5 МБ). Пишется одновременно с `listings` для каждой
успешно обработанной новой карточки и никогда не чистится.

Назначение: гарантировать, что объявление, вытесненное из `listings`
лимитом в 100 строк, не будет ошибочно принято за новое и не запустит
повторное скачивание описания, повторный вызов агента или повторное
уведомление, если оно снова попадётся в выдаче поиска.

### Таблица `search_config` (новая, одна активная строка)

```
city, brand, price_min, price_max, mileage_min, mileage_max,
year_min, year_max, query_text, search_url, updated_at
```

Поддерживается один активный поиск (не несколько параллельных — YAGNI,
текущий сценарий использования этого не требует).

## Сборка ссылки поиска Avito (`url_builder.py`)

**Важная техническая находка:** параметр `f=` в URL поиска Avito (диапазоны
цены/года/пробега) — это недокументированный проприетарный бинарный формат
(base64-JSON фрагменты, обёрнутые в нестандартную схему с символом `~`,
которого нет ни в одном стандартном base64-алфавите). Собирать эту строку
вручную означает угадывать закрытую сериализацию Avito, которая может
измениться при следующем деплое их фронтенда — противоречит принципу
проекта «не гадать разметку/форматы, брать из реальных данных».

**Решение:** не собирать `f=...` руками. При создании/изменении поиска через
UI, `url_builder.py` открывает Playwright-страницу поиска Avito, заполняет
реальную форму фильтров (поля «Марка», «Цена, ₽», «Год выпуска», «Пробег,
км» — точные `data-marker`/селекторы будут сняты с реальной формы на этапе
реализации, как и для остальных селекторов в проекте), нажимает применение
фильтров и забирает получившийся `page.url()`. Дальше этот URL используется
как обычный `SEARCH_URL` — весь остальной пайплайн скрапинга не меняется.

Эта сборка выполняется один раз при сохранении настроек поиска через
`POST /api/config` (синхронно, занимает несколько секунд — фронт показывает
индикатор загрузки), а не на каждом цикле опроса.

Если сборка не удалась (Playwright-ошибка/таймаут) — предыдущий рабочий
`search_url` не затирается, пользователю в UI показывается понятная ошибка.

## Агент релевантности (`agent.py`)

- Провайдер: **Anthropic Claude API**, модель **Claude Haiku 4.5**
  (`claude-haiku-4-5-20251001`) по умолчанию — задача классификации простая
  и частая (раз в минуту), Sonnet/Opus здесь избыточны по цене; модель
  можно переопределить в конфиге.
- Один батч-запрос за цикл на все новые карточки разом (не по одной).
- Структурированный ответ через **tool use** (принудительный вызов
  инструмента) — не парсинг свободного текста, чтобы не ловить неожиданный
  формат ответа.
- Вход: `query_text` из `search_config` + для каждой карточки title, price,
  year, mileage, description.
- Выход на каждую карточку: `{id, relevant: bool, reason: str}`.
- Кэширование: карточка, уже имеющая `agent_evaluated_at`, повторно агенту
  не передаётся.
- Ручная переоценка: кнопка «Переоценить» в UI сбрасывает
  `agent_evaluated_at` для уже сохранённых (не вытесненных) записей в
  `listings` и прогоняет их через агента заново под текущий `query_text`
  (полезно, если пользователь поменял текстовое уточнение). Автоматически
  при каждом изменении текста это не происходит — YAGNI.

## Веб-интерфейс

**Стек:** `frontend/` — Vite + React + TypeScript + Tailwind + компоненты
shadcn/21st.dev, устанавливаемые через CLI. Framer Motion для анимаций
(стандартная пара с shadcn/21st.dev-компонентами, естественнее для React,
чем ручное управление GSAP через рефы). Сборка (`npm run build`) кладёт
статику в `frontend/dist`, которую отдаёт Flask.

**Дизайн-система** (получена через `ui-ux-pro-max`, стиль запрошен
пользователем «красиво, легко читалось»):
- Стиль: **Bento Box Grid** — модульные карточки, `rounded-xl`, мягкие
  тени, hover scale 1.02, полная поддержка light/dark, низкая сложность,
  хорошая доступность (WCAG AA).
- Палитра: primary `#0F172A`/`#1E293B` (тёмный slate), акцент `#22C55E`
  (зелёный — релевантно/цена упала), `#EF4444` (красный — отклонено
  агентом/тревога).
- Типографика: **Fira Sans** для текста, **Fira Code** моноширинным для
  чисел (цена/пробег/год) — числа легче сравнивать между карточками.
- Анимация: волновое появление карточек (`stagger`, `back.out(1.4)`,
  300–450 мс) при обновлении списка; короткая цветовая вспышка на бейдже
  цены при её изменении. Обе анимации уважают `prefers-reduced-motion`.

**Компоненты (shadcn/21st.dev):**
- `Card` — карточка объявления: фото, заголовок, цена (Fira Code, крупно),
  бейджи года/пробега, короткое обоснование агента, ссылка на Avito
- `Badge` — зелёный «−N ₽» при снижении цены, серые бейджи года/пробега
- `Skeleton` — во время первой загрузки/обновления (шиммер-заливка)
- `Sonner`/`Toast` — уведомление в браузере о новых релевантных объявлениях
  между обновлениями (дополняет, не заменяет консоль/Telegram)
- `Input` / `Slider` / `Textarea` / `Button` — форма настроек поиска

**Экраны/элементы UI:**
1. Форма настроек поиска (город, марка, цена мин/макс, пробег мин/макс, год
   мин/макс, текстовое уточнение) + кнопка «Сохранить» → `POST /api/config`.
2. Список релевантных объявлений (`relevant=1`), сортировка по дате
   обнаружения, с индикатором изменения цены.
3. Строка статуса: «последняя проверка HH:MM:SS», «найдено: N»; если время
   не обновляется дольше ~2 циклов — визуальная подсветка, что фоновый
   поток, видимо, упал.
4. Кнопка «Переоценить» (ручной перезапуск агента по уже известным записям).
5. Тумблер «показать отклонённые агентом» — прозрачность решений агента.

**Обязательный чек-лист качества** (из `ui-ux-pro-max`): контраст текста
≥4.5:1, видимый фокус для клавиатурной навигации, никаких emoji вместо
иконок (SVG/Lucide), числа с разделителями разрядов («180 000 км»),
адаптивная сетка карточек (375/768/1024/1440px), `prefers-reduced-motion`.

## API-эндпоинты

- `GET /api/listings` — JSON релевантных объявлений (+ отклонённые, если
  передан флаг показа)
- `GET /api/status` — время последней проверки, число найденных, жив ли
  фоновый поток
- `GET /api/config`, `POST /api/config` — чтение/обновление
  `search_config`; `POST` синхронно запускает `url_builder.py`
- `POST /api/rescore` — ручной перезапуск агента по уже известным записям

## Секреты и конфигурация

`ANTHROPIC_API_KEY` не хранится открытым текстом в `config.py` (риск, если
проект позже попадёт в git) — читается из переменной окружения/`.env`-файла
(`python-dotenv` добавляется в `requirements.txt`, `.env` — в `.gitignore`).
README описывает, как завести ключ.

`CHECK_INTERVAL_SEC` меняется на 60 (см. риск ниже). `MIN_DELAY`/
`MAX_DELAY`/джиттер между действиями внутри одного прохода сохраняются без
изменений — они всё ещё нужны для имитации человека внутри одного цикла.
`HEADLESS` остаётся `False`.

Node.js (LTS) + npm — новая обязательная зависимость проекта, описывается в
README. Установка: `cd frontend && npm install && npm run build`, затем
`python app.py`.

## Обработка ошибок

- Фоновый цикл — тот же широкий `try/except`, что и сегодня в
  `main_loop`: логирует, не роняет Flask-сервер, пробует снова в следующем
  цикле.
- Ошибка вызова Claude API за цикл — карточки остаются неоценёнными
  (`relevant = NULL`, не пишутся в `seen_ids`), чтобы агент гарантированно
  обработал их в следующий раз, а не потерял навсегда.
- Ошибка сборки `search_url` через Playwright — понятная ошибка в UI,
  прежний рабочий `search_url` не затирается.
- Полное падение фонового потока — Flask продолжает отдавать последние
  сохранённые данные; в UI это видно по неизменной «последней проверке».

## Осознанно принятый риск: интервал в 1 минуту

CLAUDE.md проекта прямо говорит не уменьшать интервалы/задержки без явной
просьбы пользователя — это осознанная мера против блокировки по IP. Явная
просьба поступила (интервал 1 минута вместо прежних 5), поэтому реализуем
именно так, сохраняя все прочие смягчения: `HEADLESS=False`,
`MIN_DELAY`/`MAX_DELAY` между действиями браузера внутри одного прохода,
небольшой джиттер вокруг минуты (не ровно 60.000 сек). Риск временной
блокировки по IP выше, чем при интервале в 5 минут — пользователь принимает
это сознательно.

## Тестирование

Без сети (юнит-тесты):
- обрезка `listings` до 100 строк по `first_seen`;
- три ветки dedup-логики (новый / вытеснен-но-известен-в-`seen_ids` /
  известен-и-присутствует-в-`listings`);
- кэш агента — карточка с `agent_evaluated_at` повторно не передаётся;
- разбор ответа агента (мок клиента Anthropic, включая ветку ошибки API);
- Flask-роуты `/api/*` через тестовый клиент Flask с замоканными
  БД/агентом.

Сквозной прогон (реальный Avito + реальный Claude API + реальный
`url_builder.py`) — только на машине пользователя, как и сегодня описано в
CLAUDE.md для изменений в `scraper.py`. После реализации нужно явно
попросить пользователя прогнать приложение и прислать результат/лог, а не
считать изменения рабочими только по исходному коду.

## Вне рамок (сознательно не делаем)

- Несколько параллельных активных поисков — только один активный
  `search_config` за раз.
- Автоматическая переоценка уже известных записей при каждом изменении
  текстового уточнения — только по кнопке «Переоценить».
- Возврат «переоткрытых» объявлений, вытесненных лимитом в 100 строк, но
  всё ещё активных на Avito — они намеренно остаются скрытыми (см. раздел

## Дополнение 2026-08-14: капча/блокировки, пауза, живое обновление, панель фильтра

Пользователь столкнулся с блокировками по IP при реальном использовании.
Добавляем следующее (архитектурное дополнение к уже реализованному плану):

### Пауза/возобновление фонового потока

Вместо отдельного механизма для капчи и отдельного для ручной кнопки
«Стоп» — один общий флаг паузы, хранящийся в БД (`worker_status.paused`,
`worker_status.pause_reason`), а не в памяти процесса:

- `paused INTEGER DEFAULT 0`, `pause_reason TEXT` (`"manual"` или
  `"blocked"`) — новые столбцы `worker_status`.
- `db.set_paused(conn, paused: bool, reason: str | None)`.
- `db.get_status(conn)` дополнительно возвращает `paused`/`pause_reason`.
- `worker.background_loop`: в начале каждой итерации проверяет
  `db.get_status(conn)["paused"]` — если true, ничего не скрапит, коротко
  ждёт (несколько секунд) и проверяет снова. Хранение состояния в БД, а не
  в `threading.Event`, означает, что Flask-роут ставит флаг мгновенно, не
  дожидаясь фонового потока.
- `POST /api/worker/pause` → `db.set_paused(conn, True, "manual")`.
- `POST /api/worker/resume` → `db.set_paused(conn, False, None)`.
- Кнопка «⏸ Остановить парсинг» / «▶ Возобновить» в интерфейсе.

**Сознательно НЕ делаем:** автоматическое решение капчи через сторонние
сервисы, смену IP/прокси — это инструменты обхода защиты сайта и выходят
за рамки личного мониторинга (см. раздел «Важные соглашения» в
CLAUDE.md).

### Обнаружение капчи/блокировки

После загрузки страницы поиска, если ожидаемые карточки объявлений
(`[data-marker="item"]`) не появились, проверяем текст страницы на
признаки капчи/блокировки (эвристика по ключевым словам — «капч», «не
робот», «доступ ограничен» и т.п., см. `scraper.is_blocked_or_captcha`).
Если похоже на блокировку — ставим `pause_reason="blocked"` вместо того,
чтобы тут же повторить попытку в следующем цикле (что усугубило бы
блокировку). В интерфейсе — заметный баннер с объяснением и просьбой
решить капчу в открытом окне браузера (`HEADLESS=False` остаётся
как есть, окно видно) либо просто подождать, затем нажать «Возобновить».

Эвристика приблизительная — точные `data-marker` страницы блокировки
не собраны (пользователь должен прислать HTML/скриншот при следующей
блокировке, как и для любого другого нового селектора в проекте).

### Проверка, что фильтр действительно применился

`url_builder.build_search_url` теперь проверяет: если пользователь задал
хотя бы один фильтр (марка/цена/пробег/год), а итоговый URL совпал с
базовым (`https://www.avito.ru/{city}/avtomobili` без изменений) —
считаем, что заполнение формы не сработало, и поднимаем исключение
(попадает в уже существующую обработку ошибок `POST /api/config`: старый
`search_url` не перезаписывается, пользователю — понятная ошибка). Это
защита от того, чтобы случайно не начать скрапить весь список без
фильтра при незаметном сбое заполнения формы.

### Живое обновление списка

Опрос фронтендом собственного API (`/api/listings`, `/api/status`) —
это чтение локальной БД, не обращение к Avito, поэтому не связано с
блокировками. Ускоряем его с 60 до ~3 секунд, чтобы уже оценённые агентом
объявления (worker.py пишет их в БД по одному, по мере готовности
батча) появлялись на экране почти сразу, а не раз в минуту. Интервал
самого скрапинга Avito (`CHECK_INTERVAL_SEC = 60` + джиттер) — НЕ
меняется, это по-прежнему единственное сознательное отступление от
анти-бан задержек.

### Панель активного фильтра

Над списком объявлений всегда показывается сводка текущих сохранённых
критериев поиска (город/марка/цена/пробег/год/текст) — видна сразу при
загрузке страницы, а не только внутри формы редактирования.
