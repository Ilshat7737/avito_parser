# Дизайн: веб-версия монитора для поиска машин на Avito

Дата создания: 2026-08-13. Последний пересмотр: 2026-08-17 (текст ниже
описывает актуальное состояние; история решений — в разделе «История
изменений» в конце документа).

Статус: реализовано и используется, дорабатывается по мере реальной
эксплуатации.

## Контекст и цель

Исходный проект — CLI-скрипт (`main.py`), запускаемый вручную или по cron, с
настройками только через `config.py` и уведомлениями в консоль/Telegram.

Поверх него построено локальное веб-приложение для поиска **машин** на
Avito, с:
- вводом критериев поиска (город, марка, диапазон цены, диапазон пробега,
  диапазон года, произвольное текстовое уточнение) через браузер, а не
  `config.py`;
- LLM-агентом, который фильтрует и ранжирует найденные объявления по
  релевантности текстовому уточнению;
- автообновлением данных фоновым потоком (интервал и задержки — см.
  «Секреты и конфигурация»);
- строгим лимитом на размер БД (100 записей с полными данными), чтобы не
  забить диск, при этом без повторного скачивания уже виденных объявлений;
- управлением сканированием прямо из интерфейса: пауза/возобновление,
  индикатор «идёт сканирование», понятные баннеры при капче/блокировке/
  ошибке;
- красивым, легко читаемым веб-интерфейсом (React + Tailwind + shadcn).

`main.py` (CLI-режим) не тронут и продолжает работать как раньше — это
архитектурное дополнение, а не замена.

## Архитектура

Flask-приложение с двумя параллельно работающими частями, читающими и
пишущими одну и ту же SQLite-базу (`config.WEB_DB_PATH`, отдельную от
CLI-режима — см. «Секреты и конфигурация»):

- **Фоновый поток** (`threading.Thread`, daemon, запускается из
  `app.main()`) — крутится, пока жив процесс `app.py`. Каждая итерация:
  1. Проверяет `worker_status.paused` в БД — если true, ничего не
     скрапит, коротко ждёт (`PAUSE_POLL_SEC = 3` сек) и проверяет снова.
  2. Иначе — один цикл: скрапинг → dedup → (для новых, группами) описание
     → батч-вызов агента → запись в БД → уведомления → обрезка `listings`.
  3. Ждёт `CHECK_INTERVAL_SEC` + случайный джиттер до следующей итерации.

  Состояние (`paused`, `pause_reason`, `scanning`, `last_error`,
  `last_check`, `last_count`) хранится в БД (`worker_status`), а не в
  памяти процесса/`threading.Event` — Flask-роуты меняют его мгновенно,
  не дожидаясь фонового потока, и оно переживает перезапуск процесса.

- **Flask-сервер** — отдаёт собранный React-фронтенд (`frontend/dist`) как
  статику и JSON через `/api/*`. Сам ничего не скрапит, только читает/пишет
  БД и по запросу с фронта пересобирает `search_url` (см. раздел про
  `url_builder.py`).

Браузер открывает `http://localhost:{WEB_PORT}` (порт см. «Секреты и
конфигурация»). Фронтенд опрашивает `/api/listings` и `/api/status`
каждые ~3 секунды — это чтение локальной БД, не обращение к Avito, поэтому
частота опроса никак не связана с анти-бан задержками и не влияет на
риск блокировки. Частота самого скрапинга Avito регулируется отдельно
(`CHECK_INTERVAL_SEC`, `MIN_DELAY`/`MAX_DELAY` — см. ниже) и от частоты
опроса фронтенда не зависит.

`main.py --once` в консольном режиме (без веб-интерфейса) остаётся как
есть — полезен для отладки скрапинга без поднятия сервера.

### Жизненный цикл одного цикла опроса

1. Фоновый поток проверяет `worker_status.paused` — если стоит, пропускает
   весь цикл (см. «Пауза/возобновление и обработка ошибок» ниже).
2. Берёт текущий `search_url` из `search_config`. Если поиск ещё не
   настроен — ничего не делает, ждёт следующей итерации.
3. Открывает Playwright-браузер, парсит карточки со страницы поиска
   (`scraper.fetch_search_results`). Если карточки не появились —
   проверяет признаки капчи/блокировки (`scraper.is_blocked_or_captcha`);
   если похоже на блокировку — ставит паузу и переходит к шагу 7, не
   поднимая это как обычную ошибку цикла.
4. Для каждой карточки — dedup-логика:
   - уже в `listings` (не вытеснена) → проверка изменения цены/`touch`,
     агент не вызывается;
   - уже в `seen_ids`, но не в `listings` (вытеснена лимитом) → пропустить
     полностью, ничего не скачивать и не оценивать повторно;
   - совсем новый `id` → в очередь на обработку.
5. Новые карточки обрабатываются **группами** по `CHUNK_SIZE`
   (= `agent.BATCH_SIZE`, то есть без роста числа вызовов агента по
   сравнению с одним большим батчем): для группы тянутся описания, затем
   один батч-вызов агента на всю группу, затем результаты группы сразу
   пишутся в `listings`/`seen_ids` — не дожидаясь остальных групп. Это
   даёт видимость результатов на экране по мере готовности, а не одним
   куском в конце цикла (важно при задержках в десятки секунд между
   запросами — см. «Секреты и конфигурация»).
6. Уведомления (консоль/Telegram + toast в браузере) — только для карточек
   с `relevant=1`.
7. Любая непредвиденная ошибка цикла (не капча/блокировка — та
   обрабатывается отдельно на шаге 3) ставит паузу вместо повтора в
   следующем цикле — см. «Обработка ошибок».
8. После вставки новых записей — обрезка `listings` до 100 самых свежих
   строк (см. «Хранилище данных»).

## Хранилище данных

### Таблица `listings`

Столбцы: `id, title, price, url, photo, description, year, mileage,
relevant, relevance_reason, agent_evaluated_at, first_seen, last_price,
last_checked`.

- `year INTEGER` — год выпуска (парсится из заголовка карточки).
- `mileage INTEGER` — пробег (парсится из `item-specific-params`).
- `relevant INTEGER` — `NULL` = не оценено, `1` = релевантно, `0` =
  отклонено.
- `relevance_reason TEXT` — короткое обоснование от агента.
- `agent_evaluated_at TEXT` — момент оценки (`NULL`, пока не оценено).
- `last_price` — цена ДО последнего изменения (не текущая — так фронтенд
  определяет, что цена изменилась, и подсвечивает бейдж).

Используется и CLI-, и веб-режимом, но жёсткий лимит и `seen_ids`
(см. ниже) касаются только веб-режима.

**Жёсткий лимит на 100 строк.** После каждой вставки новых записей:

```sql
DELETE FROM listings
WHERE id NOT IN (
    SELECT id FROM listings ORDER BY first_seen DESC, rowid DESC LIMIT 100
)
```

`rowid DESC` — тайбрейкер: `first_seen` хранится с точностью до секунды, и
несколько записей одного цикла могут получить одинаковое значение; без
тайбрейкера порядок вытеснения при равенстве `first_seen` был бы
непредсказуем. `rowid` в SQLite монотонно растёт с порядком вставки.

Ошибка вызова агента для конкретной группы карточек не приводит к их
потере навсегда: если батч-вызов упал (rate limit, timeout, некорректный
ответ), такие карточки просто не вставляются в `listings`/`seen_ids` в
этом цикле и будут повторно обработаны в следующем.

### Таблица `seen_ids` (без ограничения размера)

```sql
CREATE TABLE seen_ids (id TEXT PRIMARY KEY, first_seen TEXT)
```

Хранит только `id` и дату первого обнаружения — без description/photo/
текста, поэтому рост неограничен по времени, но пренебрежимо мал по месту
(даже 100 000 записей — около 5 МБ). Пишется одновременно с `listings` для
каждой успешно обработанной новой карточки и никогда не чистится.

Назначение: гарантировать, что объявление, вытесненное из `listings`
лимитом в 100 строк, не будет ошибочно принято за новое и не запустит
повторное скачивание описания, повторный вызов агента или повторное
уведомление, если оно снова попадётся в выдаче поиска.

### Таблица `search_config` (одна активная строка)

```
city, brand, price_min, price_max, mileage_min, mileage_max,
year_min, year_max, query_text, search_url, updated_at
```

Поддерживается один активный поиск (не несколько параллельных — см. «Вне
рамок»).

### Таблица `worker_status` (одна строка, состояние фонового потока)

```
last_check, last_count, paused, pause_reason, last_error, scanning
```

- `paused INTEGER DEFAULT 0`, `pause_reason TEXT` (`"manual"` /
  `"blocked"` / `"error"`) — см. «Обработка ошибок».
- `last_error TEXT` — текст последней ошибки, когда `pause_reason =
  "error"`; очищается при возобновлении.
- `scanning INTEGER DEFAULT 0` — true на время выполнения цикла, для
  индикатора загрузки в интерфейсе. Гарантированно сбрасывается в
  `finally` (`worker.run_cycle_with_safety`) и дополнительно принудительно
  сбрасывается в `False` при каждом старте `app.main()` — на случай, если
  предыдущий запуск был убит не штатно (SIGKILL и подобное не даёт
  `finally` отработать), иначе индикатор «сканирую» мог залипнуть
  навсегда.

**Миграция схемы.** `worker_status` расширялась несколько раз за время
эксплуатации, и `CREATE TABLE IF NOT EXISTS` не добавляет столбцы в уже
существующую таблицу — файл БД от более старой версии кода иначе ломал
`get_status()` ошибкой `sqlite3.OperationalError`. `db.get_conn()` при
каждом открытии БД проверяет `PRAGMA table_info(worker_status)` и
добавляет через `ALTER TABLE` любые столбцы из актуальной схемы, которых
не хватает. Старые данные (`last_check`, `last_count` и т.д.) при этом не
теряются. Тот же паттерн стоит применять при следующем расширении
`worker_status`, а не рассчитывать на удаление файла БД пользователем.

## Сборка ссылки поиска Avito (`url_builder.py`)

**Техническая находка:** параметр `f=` в URL поиска Avito (диапазоны
цены/года/пробега) — недокументированный проприетарный формат (base64-JSON
фрагменты). Собирать эту строку вручную означает угадывать закрытую
сериализацию Avito, которая может измениться при следующем деплое их
фронтенда — противоречит принципу проекта «не гадать разметку/форматы».

**Решение:** `url_builder.build_search_url()` открывает Playwright-страницу
поиска Avito и заполняет реальную форму фильтров (`data-marker`-селекторы
сняты с реальной формы: `price-from/input`, `price-to/input`,
`params[164669]-from/to` — год, `params[2687]-from/to` — пробег,
`params[110000]/multiselect-*` — марка), затем забирает получившийся
`page.url()`. Дальше этот URL используется как обычный `search_url` — весь
остальной пайплайн скрапинга не меняется.

**Взаимодействие с формой — медленное и человекоподобное**, не мгновенное
программное заполнение. Живыми прогонами против реального Avito
обнаружены и исправлены две проблемы:
1. Мгновенная подстановка значения (`page.fill`) часто не долетала до
   внутреннего состояния формы — ссылка не обновлялась вовсе.
2. Посимвольный ввод без проверки иногда портил значение в замаскированном
   поле (разделитель разрядов в отображении вроде «700 000» сбивает
   курсор при переформатировании) — в одном из живых прогонов реально
   получили `{"from":700000,"to":0}` вместо ожидаемого `to=1000000`.

Текущая реализация: скролл поля в область видимости, наведение мышью,
клик, выделение и очистка текущего значения, посимвольный ввод со
случайными паузами между нажатиями — затем сверка введённых цифр с
ожидаемыми; при несовпадении — до `TYPE_RETRIES` (2) повторных попыток.
Паузы между полями (`FIELD_PAUSE_MIN`/`MAX` = 1.0–2.5 сек) и внутри набора
символа — это внутристраничное взаимодействие с уже загруженной формой,
а не отдельные запросы к сайту, поэтому они **намеренно не связаны** с
`config.MIN_DELAY`/`MAX_DELAY` (те регулируют паузу между отдельными
запросами страниц — см. «Секреты и конфигурация»).

`page.goto()` на страницу поиска использует увеличенный таймаут (60 сек
вместо дефолтных 30) — при деградации ответа Avito из-за ограничений по IP
30 секунд не всегда достаточно даже на саму загрузку страницы.

**Проверка, что фильтр действительно применился.** После заполнения формы
проверяется: если пользователь задал хотя бы один диапазонный фильтр
(цена/пробег/год), а в итоговом URL **нет параметра `f=`** — считаем, что
заполнение не сработало, и поднимаем исключение. Сравнивать итоговый URL
со «стартовым» (`https://www.avito.ru/{city}/avtomobili`) ненадёжно: сама
Avito добавляет к URL параметры вроде `?radius=200&searchRadius=200` сразу
при загрузке страницы, независимо от заполнения формы — из-за этого
сравнение «URL изменился или нет» почти всегда ложно показывало бы
«применилось», даже когда диапазонные фильтры не долетели. Проверка на
присутствие `f=` — прямая и подтверждена вручную декодированием параметра.
Марка в эту проверку не входит — подтверждённых данных о том, как она
кодируется в URL, нет.

Эта сборка выполняется один раз при сохранении настроек поиска через
`POST /api/config` (синхронно; при медленной сети из-за ограничений по IP
может занимать от нескольких секунд до примерно минуты — фронт показывает
индикатор загрузки на кнопке «Сохранить»), а не на каждом цикле опроса.

Если сборка не удалась (Playwright-ошибка/таймаут/проверка фильтра не
прошла) — предыдущий рабочий `search_url` не затирается, пользователю в
UI показывается понятная ошибка. Автоматических повторов внутри одного
вызова `build_search_url()` нет — пользователь видит ошибку и решает,
пробовать ли снова.

## Агент релевантности (`agent.py`)

- Провайдер: **Google Gemini API** (`google-genai`), модель по умолчанию
  `gemini-flash-latest` — бесплатный тариф, без привязки карты. Ключ
  берётся в Google AI Studio (`aistudio.google.com/apikey`). Модель можно
  переопределить через `AGENT_MODEL`.

  (Изначально рассматривался Anthropic Claude API — не подошёл
  пользователю по стоимости, см. «История изменений».)
- Структурированный ответ через `response_schema` (Pydantic-модели
  `ListingVerdict`/`EvaluationResult`) — не принудительный tool-use, как
  в Anthropic API, а нативный механизм structured output у Gemini, но с
  той же целью: не парсить свободный текст и не ловить неожиданный формат
  ответа.
- Список новых карточек бьётся на батчи по `BATCH_SIZE = 15` — и ради
  качества структурированного ответа (не упереться в `max_output_tokens`
  на большом батче), и ради лимита запросов/минуту бесплатного тарифа
  Gemini. Между батчами — пауза `BATCH_DELAY_SEC` (1.5 сек).
- Вход на батч: `query_text` из `search_config` + для каждой карточки
  title, price, year, mileage, description.
- Выход на каждую карточку: `{id, relevant: bool, reason: str}`.
- Ошибка вызова API (любая) — батч логируется и пропускается, возвращается
  `{}` для этого батча; вызывающий код (`process_cycle`) не пишет эти
  карточки в БД, они будут обработаны в следующем цикле.
- Кэширование: карточка, уже имеющая `agent_evaluated_at`, повторно
  агенту не передаётся (обычный цикл сканирования обрабатывает только
  новые карточки).
- **Ручная переоценка** (кнопка «Переоценить», `POST /api/rescore`):
  берёт **все** строки `listings` (`db.get_all_listings` — без разбора по
  `relevant`/`agent_evaluated_at`), прогоняет через агента под текущий
  `query_text`, и обновляет `relevant`/`relevance_reason`/
  `agent_evaluated_at` только для карточек, на которые агент реально
  вернул вердикт. Если `query_text` пуст — агент не вызывается вовсе, все
  карточки помечаются `relevant=1` с причиной «критерий не задан».

  Важно: **ничего не обнуляется заранее.** Более ранняя версия сначала
  сбрасывала `agent_evaluated_at`/`relevant` у всех строк, а потом звала
  агента — при сбое всего батча это оставляло весь список пустым до
  следующего успешного вызова (см. «История изменений»). Текущая версия
  так делать не может: карточки без вердикта просто сохраняют прежнее
  значение `relevant`.

## Веб-интерфейс

**Стек:** `frontend/` — Vite + React + TypeScript + Tailwind + компоненты
shadcn (classic CLI, `style: "new-york"`, `baseColor: "neutral"` —
`shadcn@2.10.0` конкретно, так как `shadcn@latest`/Tailwind v4 на момент
реализации оказались несовместимы с остальным стеком, см. «История
изменений»). Framer Motion для анимаций. Сборка (`npm run build`) кладёт
статику в `frontend/dist`, которую отдаёт Flask.

**Дизайн-система** (получена через `ui-ux-pro-max`, стиль запрошен
пользователем «красиво, легко читалось»):
- Стиль: **Bento Box Grid** — модульные карточки, `rounded-xl`, мягкие
  тени, hover scale 1.02, полная поддержка light/dark, хорошая
  доступность (WCAG AA).
- Палитра: primary `#0F172A`/`#1E293B` (тёмный slate), акцент `#22C55E`
  (зелёный — релевантно/цена упала), `#EF4444` (красный — отклонено
  агентом/тревога/блокировка/ошибка).
- Типографика: **Fira Sans** для текста, **Fira Code** моноширинным для
  чисел (цена/пробег/год) — числа легче сравнивать между карточками.
- Анимация: волновое появление карточек при обновлении списка; короткая
  цветовая вспышка на бейдже цены при её изменении. Обе анимации уважают
  `prefers-reduced-motion` (`MotionConfig reducedMotion="user"`).

**Компоненты (shadcn):** `Card`/`CardContent` — карточка объявления;
`Badge` — год/пробег на карточке; `Skeleton` — во время первой
загрузки/обновления; `Sonner`/`Toast` — уведомление в браузере о новых
релевантных объявлениях; `Input`/`Textarea`/`Button`/`Switch` — форма
настроек и элементы управления. `Slider` был установлен, но в форме не
используется — диапазоны цены/пробега/года вводятся парой `Input`
(от/до), это осознанно надёжнее для неограниченных диапазонов, чем
слайдер с заранее заданными границами.

**Экраны/элементы UI:**
1. Баннер блокировки/капчи (`pause_reason === "blocked"`) — заметный,
   красный, вверху страницы, просит решить капчу в открытом окне браузера
   или подождать, затем нажать «Возобновить».
2. Баннер ошибки цикла (`pause_reason === "error"`) — аналогичный, с
   текстом последней ошибки (`worker_status.last_error`).
3. Панель активного фильтра — сводка текущих сохранённых критериев поиска
   (город/марка/цена/пробег/год/текст), видна сразу при загрузке страницы,
   до формы редактирования.
4. Форма настроек поиска (город, марка, цена мин/макс, пробег мин/макс,
   год мин/макс, текстовое уточнение) + кнопка «Сохранить» →
   `POST /api/config`.
5. Строка статуса: «последняя проверка HH:MM:SS», «найдено: N», индикатор
   «⏸ парсинг приостановлен» либо спиннер «сканирую…»
   (`status.scanning`); если время не обновляется дольше ~30 минут и
   поток не на паузе — визуальная подсветка «поток мог остановиться»
   (порог поднят с изначальных 5 минут — см. «Секреты и конфигурация» про
   задержки между запросами).
6. Кнопка «⏸ Остановить парсинг» / «▶ Возобновить» — один и тот же
   переключатель обслуживает и ручную паузу, и возобновление после капчи/
   блокировки/ошибки; отдельной кнопки «продолжить с места остановки» нет
   — dedup (`seen_ids`) сам гарантирует, что при возобновлении заново
   обрабатываются только ещё не сохранённые объявления.
7. Кнопка «Переоценить» (ручной перезапуск агента по уже известным
   записям).
8. Тумблер «показать отклонённые агентом» — прозрачность решений агента.
9. Список релевантных объявлений (`relevant=1`), сортировка по дате
   обнаружения, с индикатором изменения цены. Обновляется по мере
   готовности групп внутри цикла (см. «Жизненный цикл»), не одним куском
   в конце.

**Обязательный чек-лист качества** (из `ui-ux-pro-max`): контраст текста
≥4.5:1, видимый фокус для клавиатурной навигации, никаких emoji вместо
иконок (SVG/Lucide), числа с разделителями разрядов («180 000 км»),
адаптивная сетка карточек, `prefers-reduced-motion`.

## API-эндпоинты

- `GET /api/listings` — JSON релевантных объявлений (+ отклонённые, если
  передан флаг `include_rejected=1`)
- `GET /api/status` — `worker_status` целиком: время последней проверки,
  число найденных, `paused`/`pause_reason`, `scanning`, `last_error`
- `GET /api/config`, `POST /api/config` — чтение/обновление
  `search_config`; `POST` синхронно запускает `url_builder.py`
- `POST /api/rescore` — ручной перезапуск агента по уже известным записям
- `POST /api/worker/pause` — ставит `paused=True, pause_reason="manual"`
- `POST /api/worker/resume` — снимает паузу и очищает `pause_reason`/
  `last_error`

## Секреты и конфигурация

`GEMINI_API_KEY` не хранится открытым текстом в `config.py` — читается из
переменной окружения/`.env`-файла (`python-dotenv`, `.env` — в
`.gitignore`). README описывает, как завести ключ (Google AI Studio,
бесплатно).

**Интервалы и задержки** (`config.py`) — оба отступления ниже сделаны по
прямой просьбе пользователя после столкновения с реальными ограничениями
по IP, и оба остаются в силе одновременно, не отменяя друг друга:

- `CHECK_INTERVAL_SEC = 60` (+ `INTERVAL_JITTER_SEC` джиттер) — интервал
  между циклами сканирования. Было 300 сек в CLI-режиме; для веб-режима
  сокращено до 60 по прямой просьбе.
- `MIN_DELAY`/`MAX_DELAY` = 20–30 сек (было 1.5–4) — минимальная пауза
  между отдельными запросами страниц внутри `scraper.py` (карточка поиска,
  каждая страница описания). Это отдельная, более поздняя просьба — не
  чаще 1 запроса страницы за 20 секунд.
- `HEADLESS` остаётся `False` — окно браузера видно, это осознанная защита
  от детекта автоматизации (и позволяет вручную решить капчу, если она
  появится).
- Паузы внутри `url_builder.py` (`FIELD_PAUSE_MIN`/`MAX`) — отдельные
  константы, не связаны с `MIN_DELAY`/`MAX_DELAY` (см. раздел про
  `url_builder.py`).

**Порт веб-интерфейса** — `config.WEB_PORT`, по умолчанию **5050**, не
5000: на macOS (Monterey и новее) порт 5000 системно занят AirPlay
Receiver, который отвечает браузеру 403 Forbidden вместо Flask-приложения,
при этом backend отвечает нормально на прямые запросы (curl и т.п.), что
маскирует причину. Переопределяется через переменную окружения
`WEB_PORT`.

Node.js (LTS) + npm — обязательная зависимость для сборки фронтенда.
Установка: `cd frontend && npm install && npm run build`, затем
`python app.py`.

## Обработка ошибок

Философия — **не повторять автоматически, если один раз не получилось**
(явная просьба пользователя): любой сбой цикла сканирования ставит
`worker.py` на паузу и ждёт, пока пользователь сам нажмёт «Возобновить»,
а не пробует снова на следующей итерации молча. Это отличается от
CLI-режима (`main.py`), где `main_loop` по-прежнему логирует ошибку и
автоматически пробует в следующем цикле — то поведение не менялось.

- **Капча/блокировка** обнаружена (`is_blocked_or_captcha` после сбоя
  `fetch_search_results`) → `pause_reason="blocked"`, исключение не
  поднимается — не попадает под общий случай ниже. Баннер в UI просит
  решить капчу в открытом окне браузера или подождать.
- **Любая другая ошибка цикла** (сеть, парсинг, неожиданное исключение) →
  `worker.run_cycle_with_safety` ловит исключение, логирует, ставит
  `pause_reason="error"` с текстом ошибки в `last_error`. Баннер в UI
  показывает текст ошибки и просит проверить и нажать «Возобновить».
- **Ошибка вызова Gemini API** за батч — карточки батча остаются
  неоценёнными (`relevant = NULL`, не пишутся в `seen_ids`), это НЕ
  прерывает цикл целиком (батч просто пропускается, следующие группы
  обрабатываются как обычно) — карточки будут обработаны в следующем
  цикле сканирования.
- **Ошибка сборки `search_url`** через Playwright — понятная ошибка в UI
  на `POST /api/config`, прежний рабочий `search_url` не затирается.
- **Индикатор «идёт сканирование»** (`scanning`) гарантированно
  сбрасывается в `finally` при штатном завершении цикла и дополнительно
  принудительно сбрасывается при каждом старте `app.main()` — на случай
  нештатного завершения процесса между запусками.
- Полное падение фонового потока (необработанное исключение вне
  `run_cycle_with_safety`, что не должно происходить при штатной работе)
  — Flask продолжает отдавать последние сохранённые данные; в UI это
  видно по неизменной «последней проверке» дольше ~30 минут.

## Осознанно принятые риски

CLAUDE.md проекта прямо говорит не уменьшать интервалы/задержки без явной
просьбы пользователя — это осознанная мера против блокировки по IP. Две
явные просьбы поступили и реализованы одновременно (см. «Секреты и
конфигурация»):

1. Интервал цикла сканирования сокращён с 5 минут (CLI) до 1 минуты
   (веб-режим).
2. Задержки между отдельными запросами страниц внутри цикла впоследствии
   **увеличены** (не уменьшены) с 1.5–4 до 20–30 сек — сознательный шаг
   пользователя в противоположную сторону после столкновения с реальными
   блокировками, значит правилу CLAUDE.md не противоречит.

Все прочие смягчения сохраняются: `HEADLESS=False`, видимое окно браузера
на случай ручного решения капчи, автопауза (не автоповтор) при любой
ошибке или обнаруженной блокировке. Многопоточность/смена IP через прокси
и автоматическое решение капчи сознательно не реализованы — см. «Вне
рамок».

Даже с учётом этих смягчений риск временной блокировки по IP выше, чем
был в CLI-режиме с интервалом в 5 минут без веб-функциональности —
пользователь принимает это сознательно и может в любой момент поставить
сканирование на паузу.

## Тестирование

Без сети (юнит-тесты, `pytest`):
- обрезка `listings` до 100 строк по `first_seen`/`rowid`;
- три ветки dedup-логики (новый / вытеснен-но-известен-в-`seen_ids` /
  известен-и-присутствует-в-`listings`);
- групповая (chunked) обработка новых карточек и то, что результаты одной
  группы пишутся в БД до обработки следующей;
- кэш агента — карточка с `agent_evaluated_at` повторно не передаётся;
- разбор ответа агента (мок клиента `google-genai`, включая ветки ошибки
  API, `max_output_tokens`, некорректный/неполный ответ);
- обнаружение капчи/блокировки (`is_blocked_or_captcha`) и то, что она
  ставит паузу, не поднимая исключение дальше;
- `run_cycle_with_safety` — индикатор `scanning` и авто-пауза с
  `pause_reason="error"` при любом другом исключении;
- проверка «фильтр действительно применился» (`_filters_appear_unapplied`)
  как чистая функция от URL и заданных фильтров;
- миграция схемы `worker_status` на файле БД со старой структурой;
- Flask-роуты `/api/*` через тестовый клиент Flask с замоканными
  БД/агентом/`url_builder`.

Сквозной прогон (реальный Avito + реальный Gemini API + реальный
`url_builder.py`) — только на машине пользователя, как и описано в
CLAUDE.md для изменений в `scraper.py`. После реализации нужно явно
попросить пользователя прогнать приложение и прислать результат/лог, а не
считать изменения рабочими только по исходному коду.

## Вне рамок (сознательно не делаем)

- Несколько параллельных активных поисков — только один активный
  `search_config` за раз.
- Автоматическая переоценка уже известных записей при каждом изменении
  текстового уточнения — только по кнопке «Переоценить».
- Возврат «переоткрытых» объявлений, вытесненных лимитом в 100 строк, но
  всё ещё активных на Avito — они намеренно остаются скрытыми (см. раздел
  `seen_ids`).
- **Автоматическое решение капчи** через сторонние сервисы (2captcha и
  т.п.) — это прямой инструмент обхода защиты сайта, а не просто вежливое
  поведение, выходит за рамки личного мониторинга.
- **Смена IP через прокси / многопоточный параллельный скрапинг** — по
  той же причине: инструмент обхода блокировки, а не более вежливое
  поведение. Прямая просьба пользователя это реализовать была сознательно
  отклонена (дважды — для капчи и отдельно для многопоточности).

## История изменений

Краткая хронология значимых решений после первой реализации — для
контекста, почему всё устроено именно так. Актуальное состояние полностью
описано в разделах выше; здесь — только «почему».

- **2026-08-14, капча/паузы.** Пользователь столкнулся с блокировками по
  IP. Добавлены: единый механизм паузы через БД (не `threading.Event`,
  чтобы Flask-роут ставил флаг мгновенно), эвристическое обнаружение
  капчи/блокировки, панель активного фильтра, ускорение опроса фронтендом
  собственного API (60 сек → 3 сек — не связано с частотой скрапинга
  Avito). Тогда же переписан ввод в `url_builder.py` на человекоподобный
  (посимвольный, с паузами) — первая версия просто использовала
  `page.fill()`, которая ненадёжно долетала до состояния формы.
- **2026-08-14, интервалы (2).** Ограничения по IP продолжались.
  `MIN_DELAY`/`MAX_DELAY` подняты с 1.5–4 до 20–30 сек — не чаще 1
  запроса страницы раз в 20 сек, прямая просьба. Порог «поток мог
  остановиться» в интерфейсе поднят с 5 до 30 минут, чтобы не давать
  ложную тревогу при закономерно подорожавших по времени циклах.
- **2026-08-14, индикатор и авто-пауза (3).** Прямая просьба: показывать
  индикатор загрузки во время сканирования и не пытаться бесконечно
  повторять шаг при сбое — один раз не получилось, значит ждём ручного
  вмешательства. Добавлены `worker_status.scanning`/`last_error` и
  `run_cycle_with_safety`.
- **2026-08-14→15, смена LLM-провайдера.** Anthropic Claude API оказался
  неприемлем по стоимости для пользователя (платный, отдельная
  подписка). Заменён на Google Gemini API (бесплатный тариф) — тот же
  интерфейс `evaluate_listings()`, structured output вместо
  принудительного tool-use.
- **2026-08-15, живой баг в проверке фильтра.** Первая версия проверки
  «фильтр применился» сравнивала итоговый URL со «стартовым» — сравнение
  оказалось всегда ложным из-за собственного редиректа Avito
  (`?radius=...`), появляющегося независимо от заполнения формы.
  Переписано на проверку присутствия параметра `f=`, подтверждено
  декодированием.
- **2026-08-17, реалтайм-отображение.** До этого момента `process_cycle`
  обрабатывал все новые карточки цикла целиком и писал их в БД одним
  куском в конце — при возросших (20–30 сек) задержках между запросами
  цикл с несколькими новыми объявлениями мог идти много минут без единого
  видимого результата. Переписано на групповую обработку (`CHUNK_SIZE` =
  `agent.BATCH_SIZE`, без роста числа вызовов агента) с записью каждой
  группы в БД сразу после оценки.
- **2026-08-17, авто-миграция схемы `worker_status`.** После третьего
  подряд расширения `worker_status` новыми столбцами (`paused`/
  `pause_reason`, затем `last_error`/`scanning`) стало ясно, что
  `CREATE TABLE IF NOT EXISTS` не спасает уже существующий файл БД —
  добавлена авто-миграция через `ALTER TABLE` в `db.get_conn()`.
- **2026-08-17, порт 5000 → 5050.** На macOS порт 5000 занят системным
  AirPlay Receiver, отвечающим браузеру 403 без явной ошибки на стороне
  Flask — перенесено на `WEB_PORT=5050` по умолчанию.
- **Переоценка (`/api/rescore`) переработана** параллельно с пунктом про
  индикатор/авто-паузу выше: первая версия сначала обнуляла
  `agent_evaluated_at`/`relevant` у всех записей, потом звала агента —
  при сбое всего вызова список релевантных объявлений в интерфейсе
  временно пустел. Переписано так, чтобы ничего не обнулялось заранее
  (см. «Агент релевантности»).
