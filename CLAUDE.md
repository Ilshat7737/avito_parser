# CLAUDE.md

Этот файл даёт Claude Code контекст о проекте при работе в этой директории.

## Что это за проект

Локальный монитор объявлений Avito. Периодически открывает страницу
поиска Avito через Playwright, парсит карточки объявлений, сравнивает
их с локальной SQLite-базой и уведомляет о новых объявлениях и
изменении цены (в консоль и опционально в Telegram).

Не веб-сервис, не деплоится — запускается вручную или по расписанию
(cron / Task Scheduler) на машине пользователя.

Есть два независимых режима: CLI (`main.py`, как описано выше) и
веб-режим (`app.py`, см. ниже) — у них отдельные файлы БД (`DB_PATH` и
`WEB_DB_PATH` в `config.py`), чтобы не мешать друг другу лимитом/dedup.

## Структура

- `config.py` — все настраиваемые параметры (URL поиска, интервалы,
  задержки, Telegram). Единственный файл, который обычно правит
  пользователь, а не Claude.
- `scraper.py` — вся логика Playwright: открытие страницы, парсинг
  карточек по `data-marker`-атрибутам, загрузка полного описания.
- `db.py` — тонкая обёртка над `sqlite3`. Веб-режим ведёт ДВЕ параллельные
  поисковые сессии (`session_id` 1 и 2 — два независимых окна браузера с
  разными фильтрами, см. `worker.py`/`app.py` ниже) в одном файле БД;
  CLI-режим (`main.py`) session_id нигде не передаёт, все функции по
  умолчанию используют `session_id=1`, так что его поведение и файл БД
  (`config.DB_PATH`) не меняются. Таблица `listings` хранит полные данные
  объявлений с составным ключом `(id, session_id)` и в веб-режиме жёстко
  ограничена 100 строками НА СЕССИЮ (FIFO по `first_seen`, см.
  `evict_old_listings`). Таблица `seen_ids` (только веб-режим) хранит ID
  всех когда-либо обработанных объявлений (тоже по составному ключу
  `(id, session_id)`, без ограничения размера) — не даёт повторно
  скачать/оценить/уведомить об объявлении, вытесненном из `listings`
  лимитом, но всё ещё активном на Avito; она же — механизм проверки
  "не пересеклись ли два окна" (`recently_seen_elsewhere()`, см. `worker.py`).
  Таблицы `search_config` и `worker_status` (только веб-режим) хранят
  текущие критерии поиска и состояние фонового потока КАЖДОЙ сессии
  отдельно (PK — `session_id`, а не фиксированный `id=1`, как было до
  многосессионного режима). **`worker_status` расширялась несколько раз
  за время эксплуатации** — `get_conn()` при каждом открытии БД сам
  добавляет через `ALTER TABLE`/пересоздание таблицы недостающие столбцы
  и мигрирует старые файлы БД (одна строка `id=1`) на схему с
  `session_id` (`_migrate_listings`, `_migrate_seen_ids`,
  `_migrate_search_config`, `_migrate_worker_status_columns`,
  `_migrate_worker_status_session`), потому что `CREATE TABLE IF NOT
  EXISTS` не трогает уже существующую таблицу. При следующем расширении
  схемы — мигрировать так же, а не полагаться на то, что пользователь
  удалит файл БД вручную. Несколько потоков (два воркера + Flask, все
  в одном процессе `app.py`) открывают отдельные `sqlite3.Connection`
  к одному файлу — БД в WAL-режиме (`PRAGMA journal_mode=WAL`), но ВСЕ
  операции записи (включая создание схемы в `get_conn`) дополнительно
  сериализованы процессным `db._WRITE_LOCK`: без него конкурентные
  записи из двух сессий почти сразу ловят `sqlite3.OperationalError:
  database is locked` (проверено на практике, не только в теории) — не
  убирать этот лок при рефакторинге записи.
- `notify.py` — вывод уведомлений (консоль + опционально Telegram Bot API).
- `main.py` — точка входа, цикл проверки (`process_items` сравнивает
  свежие данные с базой и решает, что это — новое объявление,
  изменение цены или ничего не изменилось).
- `requirements.txt` — `playwright`, `requests`, `google-genai`, `pydantic`, Flask.
- `README.md` — инструкция по установке и запуску для пользователя.

**Веб-режим (поиск машин с LLM-агентом):**

- `url_builder.py` — собирает `search_url` по критериям пользователя
  (город, марка, цена/пробег/год), НЕ конструируя параметр `f=` вручную —
  он недокументированный проприетарный формат Avito, который может
  измениться при следующем деплое их фронтенда. Вместо этого открывает
  реальную форму фильтров через Playwright, заполняет поля по
  `data-marker`-селекторам и забирает получившийся `page.url()`. Не
  переписывать на ручную сборку `f=`.
- `agent.py` — оценка релевантности объявлений через Gemini API
  (по умолчанию `gemini-flash-latest`, бесплатный тариф), структурированный
  JSON-ответ через `response_schema` (Pydantic), батчи по 15 объявлений
  с паузой между ними — чтобы не упереться в лимит запросов/минуту.
- `worker.py` — фоновый рабочий процесс, периодический парсинг Avito
  и вызов агента для ранжирования, хранение результатов.
  `background_loop(conn, stop_event, session_id)` параметризован
  `session_id` — `app.py` поднимает ДВА таких цикла в отдельных
  daemon-потоках (по одному на сессию 1 и 2), у каждого свой Chromium
  (новый `p.chromium.launch()` на каждой итерации внутри `do_cycle`) и
  своё соединение с БД => два реальных окна браузера работают
  одновременно, с собственными фильтрами и собственным статусом паузы/
  ошибки — сессия 1 не встаёт на паузу из-за ошибки сессии 2 и наоборот.
  Перед тем как счесть объявление новым, `process_cycle` проверяет
  `db.recently_seen_elsewhere(conn, item_id, session_id, hours=24)` —
  не забрала ли уже то же самое объявление СОСЕДНЯЯ сессия за последние
  24 часа (константа `worker.CROSS_SESSION_DEDUP_HOURS`); если да —
  пропускает его (не скачивает описание, не зовёт агента повторно, не
  шлёт повторное уведомление), но отмечает виденным и для текущей
  сессии тоже. Это и есть механизм "не пересекаться" между двумя
  окнами, о котором просил пользователь. Проверяет паузу
  (`worker_status.paused` в БД, для СВОЕЙ сессии) в начале каждой
  итерации — если стоит, ничего не скрапит. Пауза ставится либо
  вручную (кнопка «Стоп» в интерфейсе → `POST /api/worker/pause?session=N`),
  либо автоматически при обнаружении капчи/блокировки (`run_search_cycle` →
  `scraper.is_blocked_or_captcha`, эвристика по ключевым словам —
  точные `data-marker` страницы блокировки не собраны), либо
  автоматически при ЛЮБОЙ другой ошибке цикла (`run_cycle_with_safety`,
  `pause_reason="error"` + текст в `worker_status.last_error`).
  Возобновление — только вручную, кнопкой «Возобновить»: **веб-режим
  сознательно не повторяет автоматически, если цикл сломался** (в
  отличие от CLI-режима, где `main_loop` по-прежнему логирует и
  пробует снова на следующей итерации) — прямая просьба пользователя,
  чтобы не долбить заблокированный/упавший IP повторными попытками.
  Новые карточки обрабатываются группами по `worker.CHUNK_SIZE` (=
  `agent.BATCH_SIZE`) с записью каждой группы в БД сразу после оценки —
  не всем циклом разом в конце, иначе при задержках в 20–30 сек между
  запросами результаты не появлялись бы на экране очень долго.
- `app.py` — Flask-приложение, HTTP API для фронтенда (список фильтров,
  сохранение поиска, получение результатов) и точка запуска обеих
  фоновых сессий (`main()` поднимает два `background_loop`-потока,
  session_id 1 и 2, каждый со своим `db.get_conn`). Все эндпоинты,
  работающие с данными конкретной сессии (`/api/listings`,
  `/api/status`, `/api/config`, `/api/rescore`, `/api/worker/pause`,
  `/api/worker/resume`), принимают query-параметр `?session=1|2`
  (по умолчанию 1, см. `_session_id_from_request`). `/api/sessions` —
  сводка (конфиг + статус) сразу по ОБЕИМ сессиям, нужна фронтенду для
  индикаторов на переключателе вкладок без переключения на них.
- `frontend/` — React-приложение (Tailwind + shadcn/ui), собирается в
  статику (`npm run build`). `App.tsx` — переключатель между двумя
  сессиями (`SessionTabs.tsx`, живой статус обеих через `/api/sessions`),
  форма фильтров (`SearchForm.tsx`, с полем `label` — название окна) и
  сетка карточек результатов активной сессии (`ListingCard.tsx`,
  цветной акцент по `session` — `--session-1`/`--session-2` в
  `index.css`). Все запросы к API идут через `api.ts` с обязательным
  `session` в query.
- `.env.example` — шаблон переменных окружения (GEMINI_API_KEY и др.).

Данные (`avito_monitor.db`) создаются при первом запуске и в репозиторий
не входят.

## Команды

**CLI-режим (мониторинг):**

```bash
pip install -r requirements.txt
playwright install chromium

python main.py --once     # одна проверка, для отладки
python main.py            # непрерывный цикл
```

**Веб-режим (поиск с LLM):**

```bash
pip install -r requirements.txt
playwright install chromium

cp .env.example .env
# впишите в .env свой GEMINI_API_KEY (бесплатно, https://aistudio.google.com/apikey)

cd frontend
npm install
npm run build
cd ..

python app.py             # веб-сервер на http://localhost:5050 (WEB_PORT)
```

**Тесты:**

```bash
python3 -m pytest -v    # юнит-тесты db.py/scraper.py/agent.py/worker.py/app.py
```

Тестового окружения/сети в песочнице Claude нет — проверять запуск
нужно локально у пользователя. Если Claude меняет `scraper.py`, стоит
явно попросить пользователя прогнать `python main.py --once` и
прислать вывод/ошибку, а не считать изменения рабочими только по
исходному коду.

## Важные соглашения

- **Все селекторы — через `data-marker`, не через CSS-классы.**
  Классы Avito меняет часто, `data-marker` стабильнее. Если
  добавляется парсинг нового поля — сначала искать подходящий
  `data-marker` в разметке (пользователь должен прислать HTML или
  скриншот DevTools), а не гадать по классам.
- **Не убирать и не уменьшать задержки** (`MIN_DELAY`, `MAX_DELAY`,
  `INTERVAL_JITTER_SEC`) без явной просьбы пользователя — это
  сознательная мера против блокировки по IP.
- **`HEADLESS = False` по умолчанию** — осознанный выбор
  (headless-режим Playwright детектируется чаще). Не менять на
  `True` в коде по умолчанию.
- ID объявления вытаскивается regexp'ом из URL (`_extract_id` в
  `scraper.py`) — если Avito сменит формат ссылок, это первое, что
  нужно поправить.
- Все уведомления/логи — на русском языке, в том же стиле, что уже
  есть в `notify.py` (эмодзи 🆕 / 💰 + короткий текст).
- Веб-режим (`app.py`) использует интервал 60 сек по прямой просьбе
  пользователя — это единственное отступление от «не уменьшать интервалы»,
  остальные задержки (`MIN_DELAY`/`MAX_DELAY`/джиттер) не меняются.
- `MIN_DELAY`/`MAX_DELAY` увеличены до 20–30 сек (было 1.5–4) — прямая
  просьба пользователя не делать больше 1 запроса страницы за 20 сек
  после столкновения с ограничениями по IP. Регулируют паузу МЕЖДУ
  запросами страниц в `scraper.py`. Паузы ВНУТРИ уже загруженной формы
  фильтров (`url_builder.py`, между полями до нажатия Tab) — отдельные
  константы `FIELD_PAUSE_MIN`/`MAX` в самом `url_builder.py`, намеренно
  не связаны с этими — это не отдельные запросы к сайту.
- **Веб-режим ведёт ДВЕ параллельные сессии скрапинга (два окна
  браузера, session_id 1 и 2), явно запрошено пользователем** — это
  меняет прежнее правило "многопоточность для параллельного скрапинга
  не делаем". Уточнение, что именно осталось неизменным: смена IP через
  прокси/сторонние антикапчи по-прежнему НЕ делается (это инструмент
  обхода блокировки сайта, выходит за рамки личного мониторинга, см.
  пункт про капчу/171-ФЗ выше) — обе сессии работают с одного и того же
  IP пользователя, просто как два независимых окна с разными фильтрами.
  Важное следствие: `MIN_DELAY`/`MAX_DELAY` (20–30 сек) по-прежнему
  регулируют паузу МЕЖДУ запросами страниц КАЖДОЙ сессии в отдельности —
  они не пересчитаны под две сессии сразу, поэтому фактическая частота
  запросов к Avito с этого IP при двух одновременно работающих окнах
  может доходить до 2х от того, что было при одной сессии. Если
  пользователь снова столкнётся с ограничениями по IP — рассмотреть
  общий (не per-сессионный) троттлинг запросов, а не просто снова
  увеличивать `MIN_DELAY`/`MAX_DELAY`. Перед тем как считать объявление
  новым, каждая сессия проверяет `db.recently_seen_elsewhere()` — не
  забрала ли его уже соседняя сессия за последние 24 часа (см. `worker.py`
  выше) — это и есть механизм "не пересекаться" между окнами, а не
  раздельные IP/прокси.
- `GEMINI_API_KEY` — только через `.env`/переменную окружения, никогда
  не хардкодить в `config.py`.
- **Порт веб-интерфейса — `WEB_PORT` (по умолчанию 5050), не 5000.** На
  macOS (Monterey и новее) порт 5000 системно занят AirPlay Receiver,
  который отвечает браузеру 403 Forbidden вместо Flask-приложения —
  backend при этом отвечает нормально на прямые запросы (curl и т.п.),
  что маскирует причину. Не возвращать порт по умолчанию на 5000.
- Не добавлять функциональность для массового скрапинга контактов,
  телефонов или персональных данных третьих лиц без явного запроса —
  это выходит за рамки задачи (личный мониторинг) и упирается в
  152-ФЗ и пользовательское соглашение Avito.

## Типичные доработки, которые могут попросить

- Пагинация (сбор с нескольких страниц выдачи).
- Экспорт истории в CSV/Excel.
- Фильтрация по диапазону цены/ключевым словам до уведомления.
- Запуск как systemd-сервис или задача планировщика Windows.
- Больше двух параллельных сессий (сейчас в веб-режиме — ровно две,
  `session_id` 1 и 2, `db.SESSION_IDS`; CLI-режим по-прежнему один
  `SEARCH_URL` в конфиге). Расширение до N сессий потребует не только
  db.py/worker.py/app.py (сейчас захардкожено 2 — циклы `for session_id
  in db.SESSION_IDS`, `CHECK (session_id IN (1, 2))` в схеме), но и
  фронтенд (`SessionTabs.tsx` сейчас рендерит фиксированный список
  `[1, 2]`).

При такой доработке — смотреть, ложится ли она в существующие модули
(`scraper.py` / `db.py` / `notify.py` / `main.py`) без разрастания
одного файла; если логика заметно новая (например, несколько запросов
параллельно), выносить в отдельный модуль, а не пихать в `main.py`.
