# Avito Monitor

Локальный мониторинг объявлений Avito: отслеживает появление новых
объявлений и изменение цены по заданному поисковому запросу.

## Установка

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

pip install -r requirements.txt
playwright install chromium     # ставит браузер для Playwright
```

## Настройка

Откройте `config.py` и укажите:

1. **SEARCH_URL** — ссылка на страницу поиска Avito с нужными фильтрами
   (город, категория, цена и т.д.). Проще всего настроить фильтры прямо
   на сайте и скопировать адрес из браузера.
2. При желании — интервал проверки, Telegram-уведомления и т.д.

## Запуск

```bash
python main.py            # непрерывный мониторинг, Ctrl+C для остановки
python main.py --once     # одна проверка (удобно вызывать по cron / Task Scheduler)
```

Найденные объявления сохраняются в `avito_monitor.db` (SQLite) —
файл можно открыть, например, DB Browser for SQLite, чтобы посмотреть
всю историю.

## Веб-режим: поиск машин с LLM-агентом

Дополнительно к CLI-режиму (`python main.py`) есть локальное веб-приложение
для поиска машин с фильтрацией и ранжированием через Gemini.

### Установка

```bash
pip install -r requirements.txt
playwright install chromium

cp .env.example .env
# впишите в .env свой GEMINI_API_KEY (бесплатно, https://aistudio.google.com/apikey)

cd frontend
npm install
npm run build
cd ..
```

Требуется Node.js (LTS) и npm — только для сборки фронтенда, самому
приложению во время работы Node.js не нужен.

### Запуск

```bash
python app.py
```

Откройте `http://localhost:5050` (порт 5050, не 5000 — на macOS порт 5000
занят системным AirPlay Receiver и отвечает 403; при желании можно
поменять через переменную окружения `WEB_PORT`) — заполните форму поиска (город
латиницей, например `kazan`, марка, диапазоны цены/пробега/года,
текстовое уточнение) и нажмите «Сохранить». Приложение соберёт ссылку
поиска через реальную форму фильтров Avito (несколько секунд), после чего
раз в минуту будет опрашивать выдачу, оценивать релевантность через
Gemini и показывать подходящие объявления.

**Внимание:** интервал в 1 минуту — сознательно ускоренный (обычно
рекомендуется не чаще раза в 5 минут, см. `CLAUDE.md`) и повышает риск
временной блокировки по IP.

**Две независимые поисковые сессии.** По умолчанию открытая страница —
это сессия 1. Откройте отдельное окно/вкладку на
`http://localhost:5050/?session=2`, чтобы настроить второй, независимый
поиск (свои город/марка/цена/текст, свои результаты) — обе сессии
опрашиваются по очереди одним и тем же фоновым процессом (без
параллельного скрапинга, частота запросов к Avito не растёт), поэтому
при двух настроенных сессиях каждая из них обновляется примерно вдвое
реже, чем при одной. Если объявление подходит под фильтры обеих
сессий, оно достаётся только той, что оценила его релевантным первой —
вторая не увидит его повторно ближайшие 24 часа.

### Особенности веб-режима

- Хранятся только 100 самых свежих объявлений одновременно **на каждую
  сессию** (старые вытесняются автоматически) — это защита от
  разрастания базы, а не баг. Объявление, вытесненное лимитом, но всё
  ещё активное на Avito, **не** появится повторно — так задумано, чтобы
  не спамить повторными уведомлениями.
- Кнопка «Переоценить» пересчитывает релевантность уже сохранённых
  объявлений под текущее текстовое уточнение (полезно, если вы его
  поменяли) — автоматически при каждом изменении текста это не происходит.
- Тумблер «показать отклонённые агентом» показывает и те объявления,
  которые агент счёл нерелевантными — для прозрачности его решений.

## Как это устроено

- `scraper.py` — открывает страницу поиска в браузере (Playwright) и
  парсит карточки по атрибутам `data-marker` (они меняются реже, чем
  CSS-классы). Для новых объявлений дополнительно заходит на страницу
  объявления за полным описанием.
- `db.py` — хранит уже виденные объявления в SQLite, чтобы отличать
  новые от старых и ловить изменение цены.
- `notify.py` — выводит уведомления в консоль и опционально шлёт их в
  Telegram.
- `main.py` — цикл: проверка → сравнение → уведомление → пауза (с
  небольшим случайным разбросом, чтобы не стучаться в одно и то же
  время).

## Важно

- Avito ограничивает частоту запросов и может временно блокировать по
  IP при слишком активном парсинге — не уменьшайте `CHECK_INTERVAL_SEC`
  слишком сильно и не убирайте задержки в `config.py`.
- Массовый сбор чужих объявлений может противоречить пользовательскому
  соглашению Avito, а сбор персональных данных (телефоны, адреса и
  т.п.) регулируется 152-ФЗ — используйте инструмент для мониторинга
  собственного интереса (например, поиска покупки), а не для
  накопления баз данных о третьих лицах.
- Разметка сайта время от времени меняется — если парсер перестал
  находить объявления, проверьте актуальные `data-marker` в DevTools
  браузера (F12 → выделить карточку объявления).

## Домашнее задание: две поисковые сессии

Этот проект использован как «свой пет-проект» для домашнего задания
курса. Полная спецификация — `SPEC.md`, журнал по сессиям работы с
агентом — `sessions/`, правила проекта — `AGENTS.md`.

**Что сделано.** В веб-режим добавлена поддержка двух независимых
поисковых сессий (`?session=1`/`?session=2` в URL) с разными фильтрами
и разными результатами. Фоновый воркер обслуживает обе сессии по
очереди в одном потоке и одном браузере — без параллельного
скрапинга и без роста частоты запросов к Avito. Объявление, подходящее
под фильтры обеих сессий и признанное релевантным одной из них,
не показывается второй в течение 24 часов (кросс-сессионный дедуп);
отклонённые объявления такой блокировки не создают. Миграция
существующей базы `avito_monitor_web.db` на новую схему — автоматическая
и атомарная (безопасна даже при обрыве процесса посреди миграции,
что реально произошло дважды в ходе разработки — ноутбук уходил в сон).
74 юнит-теста, полный набор проходит.

**Визуальный редизайн** сделан отдельным шагом *после* фичи с сессиями
(отдельный промпт, задание прямо советует не мешать дизайн с правкой
логики) — тема сменена с шаблонного «тёмный фон + один зелёный акцент»
на automotive-стиль: у каждой сессии свой акцентный цвет (янтарный/
голубой), переключатель сессий оформлен сегмент-табами с живым статусом
обеих сессий сразу, цифры (цена/год/пробег) — моноширинным шрифтом.
Часть компонентов (пилюля статуса, стиль вкладок) взята с 21st.dev по
прямой просьбе пользователя. Логика при этом не менялась — только
`index.css`, `tailwind.config.ts`, вёрстка компонентов и один новый
компонент-переключатель.

**Что не сделано.**
- Живой прогон миграции на реальном файле `avito_monitor_web.db` с
  историческими данными пользователя — такого файла на момент
  проверки в репозитории не оказалось, миграция проверена юнит-тестами
  на синтетических данных (включая тест на обрыв процесса посреди
  миграции) и вручную на свежесозданном файле.
- Полноценный «наивный прогон» (один промпт без спеки и правил) —
  выполнен на отдельной, соответствующей заданию доработке (та же
  задача, что и спека-версия — две сессии), а не на всём проекте
  целиком, поскольку сам `avito_parser` уже существовал до начала
  работы над этим заданием и «наивно прогнать» его заново было бы
  нечестным сравнением.

**Сравнение наивного прогона и версии по спеке.** Наивный прогон — ветка
`naive-run` в этом же репозитории (запушена, **не смержена** в `main` —
специально, чтобы не путать с итоговым решением). Один и тот же
исходный запрос («сделай два окна поиска, чтобы не пересекались, с
проверкой на 24 часа»), без спеки и без `AGENTS.md`:

| | Наивный прогон (`naive-run`) | Версия по спеке (`main`) |
|---|---|---|
| Параллельность | Настоящая многопоточность — два потока/браузера Playwright скрапят одновременно | Чередование в одном потоке — параллельности нет |
| Нагрузка на Avito | Удваивается (сам агент это признал в отчёте) | Не растёт — не больше 1 запроса за интервал, как и раньше |
| Правило «не делаем параллельный скрапинг» из `CLAUDE.md` | Само-отредактировал `CLAUDE.md`, заявив, что правило «упразднено» — без вопроса | Не тронуто; соблюдено через архитектуру, а не переписыванием правил |
| Гонка записи в SQLite от двух потоков | Обнаружил и закрыл глобальной блокировкой на все операции записи | Не возникает — писатель всегда один (один поток) |
| Дизайн интерфейса | Переписал попутно, вместе с логикой, в одном коммите | Сознательно не делался в этом цикле — отдельный будущий шаг |
| Тесты | Есть, автор считает их достаточными | 74 теста, включая тест на обрыв процесса посреди миграции и два ревью (по задаче + по всей ветке) |

Вывод не в пользу «наивный хуже, спека лучше» вообще — модель наивного
прогона по-своему рабочая и решает задачу. Дело в другом: без спеки и
правил модель сама, без вопроса, приняла решение, прямо нарушающее уже
зафиксированную договорённость проекта — и не сообщила об этом как о
риске, а задним числом переписала правило под свой результат. Именно
это спека и правила предотвращают.

**Допущения** — см. `SPEC.md`, раздел «Допущения» (24-часовое
окно дедупа зашито константой, ровно 2 сессии без возможности добавить
третью, лимит в 100 объявлений действует на каждую сессию отдельно).
