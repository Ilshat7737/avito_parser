===========================================================================
КАК МЫ ПОСТРОИЛИ ВЕБ-ПРИЛОЖЕНИЕ ПОИСКА МАШИН НА AVITO
Хронология работы, использованные агенты и что получилось в итоге
===========================================================================

Этот файл — не техническая документация (она в CLAUDE.md и в
docs/superpowers/specs/), а рассказ о том, КАК велась работа: какие
инструменты/агенты использовались, где работа шла параллельно, а где
строго по одному, и что в итоге получилось.


---------------------------------------------------------------------------
1. С ЧЕГО НАЧАЛОСЬ
---------------------------------------------------------------------------

Исходная точка — консольный скрипт (main.py) для мониторинга объявлений
на Avito: открывает страницу через Playwright, парсит карточки, сравнивает
с локальной SQLite-базой, уведомляет о новых объявлениях и изменении цены.

Первые шаги в этой сессии:
  1. "Изучи репозиторий" — разбор существующей архитектуры.
  2. "Прогони проект на баги" — статический анализ и симулированные
     прогоны (реальной сети/браузера в песочнице не было), найдено
     4 замечания, главное из которых: FETCH_FULL_DESCRIPTION повторно
     скачивал описания ВСЕХ карточек каждый цикл, а не только новых.
  3. Большая задача: превратить консольный скрипт в локальное
     веб-приложение для поиска МАШИН с LLM-агентом, вводом критериев
     через браузер и автообновлением.


---------------------------------------------------------------------------
2. ПРОЕКТИРОВАНИЕ — ДО ЕДИНОЙ СТРОКИ КОДА
---------------------------------------------------------------------------

Использован процесс "брейнсторминг" (skill superpowers:brainstorming):
задача классифицирована как архитектурная (новая подсистема, не мелкая
правка) — значит, сначала диалог и дизайн, потом код, а не наоборот.

Шаги:
  - Уточняющие вопросы пользователю по одному (что делает "агент":
    фильтрация+ранжирование; как вводятся критерии: через интерфейс;
    какой LLM-провайдер; как устроен веб-бэкенд: Flask+polling).
  - Пользователь прислал реальный HTML/скриншот формы фильтров и карточки
    объявления Avito — селекторы для парсинга брались из этого дампа, а
    не угадывались (в проекте это жёсткое правило: все селекторы —
    через data-marker, разметка снимается с реальной страницы).
  - Найдена ключевая техническая развилка: параметр f= в ссылке поиска
    Avito — недокументированный проприетарный формат. Решение — не
    собирать его руками, а водить настоящую форму фильтров через
    Playwright и забирать готовую ссылку.
  - Дизайн-система веб-интерфейса подобрана через skill ui-ux-pro-max
    (поиск по локальной базе стилей/палитр/шрифтов) — стиль Bento Box
    Grid, тёмная slate-палитра с зелёным/красным акцентом, Fira Sans +
    Fira Code.
  - Спека записана в docs/superpowers/specs/2026-08-13-car-search-web-app-design.md,
    самопроверена на противоречия и пробелы, одобрена пользователем.


---------------------------------------------------------------------------
3. ПЛАН РЕАЛИЗАЦИИ
---------------------------------------------------------------------------

Skill superpowers:writing-plans превратил спеку в пошаговый план:
docs/superpowers/plans/2026-08-13-car-search-web-app.md — 11 задач
(db.py, scraper.py, url_builder.py, agent.py, config/секреты, worker.py,
app.py, фронтенд-каркас, фронтенд-компоненты, документация, ручная
сквозная проверка), в каждой — точный код, а не общие описания (правило
плана: "никаких TODO/заглушек", инженер должен суметь выполнить задачу,
не додумывая детали).

Проект на тот момент не был git-репозиторием вообще — пришлось сначала
сделать git init и базовый коммит, потом создать изолированный git
worktree под эту работу (ветка worktree-car-search-web-app) — вся
дальнейшая работа шла в нём, не трогая основную ветку напрямую.


---------------------------------------------------------------------------
4. РЕАЛИЗАЦИЯ ЧЕРЕЗ СУБАГЕНТОВ — КАК ЭТО РАБОТАЛО
---------------------------------------------------------------------------

Использован процесс superpowers:subagent-driven-development. Главное
правило, которое определяет ответ на вопрос "сколько агентов работало
параллельно":

    АГЕНТЫ-ИСПОЛНИТЕЛИ И АГЕНТЫ-РЕВЬЮЕРЫ ЗАПУСКАЛИСЬ СТРОГО ПО ОДНОМУ,
    НИКОГДА ПАРАЛЛЕЛЬНО.

Это осознанное ограничение процесса (не техническое): параллельные
исполнители могли бы одновременно менять одни и те же файлы и
конфликтовать друг с другом. Поэтому весь конвейер был последовательным:

    для каждой задачи из плана:
        1. запустить агента-исполнителя (пишет код + тесты + коммитит)
        2. запустить агента-ревьюера (независимо проверяет диф)
        3. если ревью нашло проблему — запустить агента-исправителя,
           потом агента, который проверяет именно это исправление
           (повторить до 5 раз, дальше — решение принимает управляющая
           сессия сама)
        4. следующая задача — только после того, как предыдущая закрыта

Один "управляющий" процесс (эта сессия, модель Sonnet 5) дирижировал
всем этим: готовил каждому агенту его личное задание (не весь план
целиком — только нужный кусок с точным кодом), решал, что делать при
разногласиях между агентами, вёл журнал решений.

Модели подбирались по сложности задачи, не всегда самая мощная:
  - Haiku (дешёвая, быстрая) — для механических задач, где план уже
    содержал готовый код: db.py, scraper.py, agent.py, url_builder.py,
    документация, большинство маленьких исправлений.
  - Sonnet (стандартная) — для задач, требующих больше интеграционного
    суждения: worker.py, app.py, обе фронтенд-задачи, часть ревью.
  - Opus (самая мощная) — только для финального сквозного ревью всей
    ветки целиком и проверки итоговой волны исправлений: там нужен был
    самый широкий взгляд на систему.

За всё время реализации плана было запущено порядка 35-36 отдельных
запусков субагентов (исполнители + ревьюеры + повторные проверки после
исправлений) — все строго последовательно, один за другим.

Что нашли и исправили сами субагенты в процессе (независимая проверка
себя не обманешь):
  - db.py: эвикшн по 100 строкам без тайбрейкера был бы недетерминирован
    при одинаковой секунде — добавлен rowid как вторичный критерий.
  - url_builder.py: браузер не закрывался при исключении — обёрнуто в
    try/finally.
  - agent.py: битый ответ модели мог уронить весь батч оценки —
    добавлена защита по отдельной записи.
  - app.py: собственный роут Flask для статики незаметно перекрывал
    SPA-фолбэк — из-за этого при обновлении страницы на прямом URL
    был бы 404.
  - фронтенд: не хватало части токенов дизайн-системы shadcn (кнопки/
    карточки рендерились бы без стиля); дублирующийся toast на каждый
    опрос API из-за устаревшего замыкания в React; форма не подхватывала
    уже сохранённые настройки при загрузке.

Финальное сквозное ревью (Opus) на всей ветке целиком нашло ещё 7 более
серьёзных проблем разом (в их числе: агент мог обрезать ответ на
реалистичном объёме объявлений; переоценка могла на время опустошить
список при сбое API; CLI- и веб-режим делили одну БД и могли повредить
друг другу лимит) — все исправлены одной волной правок и одной
повторной проверкой, как и предписывает процесс.

После этого — superpowers:finishing-a-development-branch: ветка
осталась как есть (не смержена в master), чтобы пользователь мог сам
прогнать приложение вживую перед принятием решения.


---------------------------------------------------------------------------
5. ЧТО ПОЛУЧИЛОСЬ ПОСЛЕ ПЕРВОГО ЭТАПА
---------------------------------------------------------------------------

Рабочее веб-приложение: Flask-бэкенд + React-фронтенд, LLM-агент
(изначально на Claude Haiku), фоновый поток сканирования раз в минуту,
лимит базы в 100 записей с бессрочной памятью о вытесненных ID, 34
юнит-теста, всё закоммичено в отдельную ветку.


---------------------------------------------------------------------------
6. ДОРАБОТКИ ПОСЛЕ ПЕРВОГО ЗАПУСКА — БЕЗ СУБАГЕНТОВ, НАПРЯМУЮ
---------------------------------------------------------------------------

Когда пользователь начал реально пользоваться приложением, вскрылись
вещи, которые нельзя было предугадать на этапе планирования — их
исправляли уже не через конвейер субагентов, а напрямую в этой же
сессии, часто с живой диагностикой против настоящего сайта Avito:

  - Смена LLM-провайдера: платный Anthropic API не устроил пользователя
    по цене — переведено на бесплатный Google Gemini API (тот же
    интерфейс агента, structured output вместо принудительного tool-use).
    Пользователь прислал реальный ключ прямо в чат — сохранён только в
    локальный .env (в .gitignore), с явным предупреждением, что раз ключ
    попал в переписку, его стоит считать потенциально засвеченным.

  - Живая диагностика реальных багов. Несколько раз запускался
    самостоятельный Python-скрипт (не через тестовый мок, а против
    настоящего avito.ru) — так нашли: что мгновенная подстановка
    значения в поле формы ненадёжна; что посимвольный ввод без проверки
    иногда портит значение из-за маски форматирования (реально получили
    цену "до 0" вместо "до 1000000" в живом запросе); что проверка
    "URL изменился" всегда врала из-за собственного редиректа Avito.
    Каждая находка — с воспроизведением, декодированием ответа сайта и
    проверкой исправления тем же живым способом.

  - Функциональность капчи/блокировок: по прямой просьбе пользователя
    рассмотрел два пути — автоматическое решение капчи через сторонние
    сервисы и смену IP через прокси. Оба отклонены сознательно: это
    инструменты обхода защиты сайта, а не просто "вежливое" поведение,
    выходят за рамки личного мониторинга. Вместо этого — обнаружение
    капчи/блокировки по эвристике и пауза с ожиданием, пока пользователь
    сам не решит капчу в открытом окне браузера и не нажмёт "Возобновить".

  - Задержки между запросами увеличены с 1.5-4 до 20-30 секунд (прямая
    просьба пользователя после столкновений с ограничениями по IP).

  - Индикатор "идёт сканирование" и правило "один раз не получилось —
    не повторяем автоматически, ждём человека" для любой ошибки цикла.

  - Реалтайм-отображение: раньше все новые объявления цикла копились
    и писались в базу одним куском в самом конце — при возросших
    задержках это означало долгое ожидание без единого результата на
    экране. Переписано на запись результатов группами по мере готовности.

  - Порт 5000 → 5050: на macOS порт 5000 системно занят Apple AirPlay
    Receiver, который отвечает браузеру 403 вместо нашего сервера —
    находка через прямое сравнение поведения curl и настоящего браузера.

  - Аудит и рефакторинг спеки: спека дополнялась четырьмя разделами
    "Дополнение" по ходу доработок, но основной текст не обновлялся —
    в нём накопились прямые противоречия (например, всё ещё упоминался
    Claude вместо Gemini, старые задержки, старое поведение при ошибках).
    Спека и CLAUDE.md приведены в соответствие с реальным кодом, история
    решений сжата в один раздел "История изменений" в конце документа.


---------------------------------------------------------------------------
7. ПРО "ПОТОКИ" (THREADS) — ЧТО РЕАЛЬНО РАБОТАЕТ ПАРАЛЛЕЛЬНО
---------------------------------------------------------------------------

Здесь два разных смысла слова "поток", и параллельность в них разная:

  а) Потоки субагентов (разговоры с ИИ) — см. раздел 4 выше: строго
     последовательно, никогда параллельно, по правилам процесса.

  б) Программные потоки внутри самого приложения (threading.Thread в
     Python) — здесь параллельность настоящая, но её всего два:
       - главный поток Flask отвечает на HTTP-запросы браузера
         (страница, /api/listings, /api/status и т.д.);
       - один фоновый daemon-поток (background_loop в worker.py) крутит
         цикл сканирования Avito.
     Они читают и пишут одну и ту же SQLite-базу без блокировок между
     собой — состояние (пауза/статус/ошибка) хранится прямо в базе,
     поэтому Flask-роут может мгновенно поставить приложение на паузу,
     не дожидаясь, пока фоновый поток сам это заметит.
     Многопоточного/параллельного скрапинга с нескольких IP в проекте
     нет — это было отдельно запрошено пользователем и осознанно
     отклонено (см. раздел 6) как инструмент обхода защиты сайта.

8. ЧТО ЕСТЬ СЕЙЧАС
---------------------------------------------------------------------------

  - CLI-режим (main.py) — работает как и раньше, не тронут.
  - Веб-режим (app.py, порт 5050) — поиск машин по городу/марке/цене/
    пробегу/году/свободному текстовому уточнению; критерии применяются
    через настоящую форму фильтров Avito, не угадыванием формата ссылки.
  - LLM-агент на Google Gemini (бесплатный тариф) фильтрует и ранжирует
    объявления по текстовому уточнению, батчами, с кэшированием оценки.
  - База ограничена 100 записями с полными данными, но помнит вообще
    все когда-либо виденные ID бессрочно — не будет скачивать и
    оценивать повторно то, что уже вытеснено лимитом.
  - Пауза/возобновление, индикатор сканирования, баннеры при капче/
    блокировке/ошибке, панель активного фильтра, реалтайм-обновление
    списка — управление и видимость происходящего прямо из интерфейса.
  - Задержки и порядок работы намеренно медленные и человекоподобные
    (видимое окно браузера, случайные паузы, посимвольный ввод) — это
    сознательный компромисс в пользу меньшего риска блокировки, а не
    недоработка.
  - 55 юнит-тестов, вся история решений — в docs/superpowers/specs/ и
    docs/superpowers/plans/, актуальные инструкции — в CLAUDE.md и
    README.md.
  - Ветка работы (worktree-car-search-web-app) не смержена в master —
    ждёт, пока пользователь лично прогонит приложение вживую и решит,
    что делать с веткой дальше (см. README.md для инструкции запуска).
